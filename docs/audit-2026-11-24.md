# Audit, 2026-11-24: first run on a new machine, and the state of the code

Machine: Windows 11, Intel i7-12700KF, **NVIDIA RTX 5070** 12 GB, 32 GB RAM.
Build: `cargo build --release -p victory` at `4e17478`, Rust 1.98.1, no
environment switches. A first run with an **empty shader and pipeline cache**,
from boot through the menus into the opening cutscene and the first room,
about 13 minutes. The game was closed by hand; nothing crashed and nothing
was written to `crashes.log`.

## What was seen

| Stage | Seen |
|-------|------|
| Boot, menus | 30 fps, steady, as upstream reports |
| Intro and cutscene | they play, but the images seem to overlap, as if each frame were shown twice |
| Cutscene and first room | 0-2 fps. Objects appear very slowly. After a while: hair, eyes, teeth, the window, the view outside and sunlight, but **no skin or body** on the main character |

| +1.5 min | 0.6 | 1,617 | 283 (124) | 98 | 1,718 | **3,070** | 1,089 |

What follows from it:

1. **For the first 8-10 minutes, thousands of draws a frame were dropped**
   because about 1,000 host pipelines were still being made (a first run:
   0 cache hits). A draw without its pipeline is skipped
   (`VICTORY_PIPELINE_WAIT_MS`, default 500 ms a frame). This is the slow
   pop-in, and the most likely reason the character's body was missing while
   the hair, eyes and teeth (other pipelines) were drawn. The cache now holds
   about 500 MB (`victory-data\cache`), so the next run should start with far
   fewer missing pipelines.
2. **Texture preparation dominated those frames**: up to 3.7 s a frame on
   the CPU, detiling and uploading. A changed texture is detiled whole, not
   only the pages written (`crates/victory-gpu/src/texture.rs:13`), and the
   texture budget filled up ("textures picked by index: the card has no room
   for more; they wait").
3. **Steady state is about 2 fps**: around 150 ms of CPU preparation and
   230-300 ms of GPU time a frame. The card was busy about half the time and
   stood idle while the submitting thread worked, because every submission is
   waited for and CPU and GPU never overlap
   (`crates/victory-gpu/src/host.rs:4`). The fork's README reports 420-450 ms
   by default on an RTX 4070, so this machine matches it.
4. **320-390 draws a frame are dropped for good**, for these reasons:

   | Warning | Count | What it means |
   |---------|-------|---------------|
   | shader does not translate | 9 shaders (5 compute, 4 pixel) | Their draws are dropped. Reasons: a descriptor read only as data (3 pixel), `v_cvt_f32_f64` (2), `v_permlanex16_b32`, a lane mask exchanged where not every lane runs, a descriptor's address or format read as data, the first half of an interpolation |
   | host pipeline refused, E_INVALIDARG | 4 compute + 1 mesh/pixel | D3D12 rejects the translated pipeline: a translator or root-signature bug, possibly specific to this GPU or driver |
   | host pipeline refused, E_OUTOFMEMORY | 1 compute (`17af15c4015cb4b6`) | The driver ran out of memory making it |
   | a pipeline creation method that is not implemented | 29 calls, slot `0x218` | The title goes without those pipelines (`crates/victory-gpu/src/device.rs:357`) |
   | a dispatch without a host pipeline dropped | ongoing | The result of the above |

5. **The view heap is capped**: the title asks for 1,245,184 shader-visible
   views and NVIDIA allows 1,000,000, so views past about 737,000 read a null
   slot (`crates/victory-gpu/src/descriptor/host.rs:580`). The fork notes the
   title's highest view seen as about 720,000, so this is probably harmless
   today, but it is a latent source of missing textures.
6. **Slow host submissions** of 450-650 ms, each running 14-20 compute
   pipelines in one list (the same set every time): a candidate for the
   first profiling pass (`VICTORY_GPU_TIMING=1` in a diagnostics build).
7. Harmless: 4 console CPU instructions emulated (`insertq`, `clzero`), the
   title refused `rpcrt4.dll`, one constant buffer not 256-byte aligned, and a
   pipeline that wants a depth-bounds test the host leaves out.

**Not yet explained: the doubled, overlapping frames.** The log does not
show their cause. Leads: the title loads AMD FidelityFX (upscaling and
possibly frame generation), whose generated frames or history would ghost if
motion vectors or history buffers are wrong; or temporal anti-aliasing
history. A diagnostics build with `VICTORY_CAPTURE` and
`VICTORY_DUMP_TARGETS=1` would show what each presented frame holds.

## The code

About 107,000 lines of Rust in 11 crates, 223 commits (upstream VIctory
history, then one squashed commit for this fork's changes, then nine more on
top). CI runs clippy and the tests (`.github/workflows/ci.yml`).

`cargo test --workspace --release` on this machine: **496 passed, 0 failed,
7 ignored**, including the 210 shader tests (62 s) that run emitted DXIL on
the RTX 5070 and compare it with reference results. So the translator's
tested paths behave on this GPU, and the refused pipelines above are not
caught by the test suite.

| Crate | Lines | What it does |
|-------|-------|--------------|
| `victory-shader` | 41,197 | Console GPU (RDNA2, GFX10) shader code to DXIL. `emit/lower.rs` alone is 11,357 lines |
| `victory-gpu` | 36,008 | The console graphics API on Direct3D 12: command lists, descriptors, textures, title-memory copies, presentation |
| `victory-hle` | 18,065 | The console's system libraries: memory, files and DirectStorage, saves, input, audio, network |
| `victory-formats` | 4,365 | Texture tiling, BCPack, XMA and other formats |
| `victory-loader` | 3,645 | Loads the title's executable and DLLs into our process; emulates console-only CPU instructions |
| `apps/victory` | 1,855 | The command line (`run`, `translate`, `inspect`, ...) |
| `victory-pe`, `-core`, `-pipeline`, `-game`, `xtask` | 1,804 | Executable parsing, shared types, build helpers |

Markers in the code:

- **157 `shortcut:` comments** where the code approximates the console
  (76 in `victory-gpu`, 52 in `victory-shader`, 23 in `victory-hle`). They
  are the to-do list. The ones most relevant to what was seen:
  - `victory-gpu/src/host.rs:4`: no CPU/GPU overlap (speed).
  - `victory-gpu/src/texture.rs:13`: whole-texture detiling (speed, pop-in).
  - `victory-gpu/src/list.rs:1668`: draws dropped until their shaders translate.
  - `victory-gpu/src/list.rs:1337`: GPU queries return plausible values, not real ones.
  - `victory-gpu/src/pipeline/host.rs:108`: no depth-bounds test.
  - `victory-hle/src/modules/display.rs:61`: no HDR output.
  - `victory-hle/src/modules/dsp.rs:15`: no reverb (zeros).
  - `victory-hle/src/modules/speech.rs:4`: silent speech.
- **4 TODOs**, no `todo!()` or `unimplemented!()`: unsupported things are
  logged and skipped, not crashed on.
- **139 `VICTORY_*` environment switches**, most of them experiments that are
  off by default. The speed switches the README names (`VICTORY_RELAY=2`,
  `VICTORY_LATE_WAIT=3`, `VICTORY_WIDE_BACK=1`, `VICTORY_CARD_BUFFERS_*`)
  are untried on this machine.
- **Ray tracing**: the title's bounce light and shadows are traced in its own
  compute shaders. The pieces translate (59 of 64 trace programs) but nothing
  runs end to end yet, so everything in shadow is black
  (`docs/fork-ray-tracing.md`).

## Second run: diagnostics build with frame capture

`cargo build --profile diag -p victory --features diagnostics`, run with
`VICTORY_CAPTURE`, `VICTORY_CAPTURE_WORLD=1` and consecutive frames listed
(`VICTORY_CAPTURE_FRAMES=600..607`, `VICTORY_CAPTURE_WORLD_ALSO=40..47`).

- **The character's body now draws.** The pipelines were all made during
  the loading screens (about 1,400 queued, 0 left when the cutscene began),
  so no draw went without its pipeline when the world began. Faces are
  black where the sun does not reach them, as expected without the
  ray-traced light.
- **The shader cache gave 0 hits** (1,958 translations), because its key is
  the hash of our own executable (`crates/victory-gpu/src/shader_cache.rs:42`).
  Every rebuild, and the diagnostics build as against the release one, starts
  from an empty cache: about two minutes of translation, and the first-run
  dropped draws again. Worth changing for development (key on the
  translator's inputs, not the whole executable).
- **The repeating frames in the intro are real and measurable.** The
  presented intro frames repeat *exactly* in a cycle of three: frames 601,
  604 and 607 are identical byte for byte, as are 602 and 605, and 603 and
  606. Those frames draw a movie: three 8-bit planes (Y, Cb, Cr) turned into
  colour with the usual YCbCr constants (1.402, -0.714). A movie that
  stalls shows one frame repeated; a fixed cycle of three means the decoder
  keeps writing new frames into a ring of three texture sets and the host
  copies of those textures are not brought up to date, so the window cycles
  through three stale pictures. This is the "each frame plays twice" seen in
  the intro. Next: watch whether the planes' title memory changes between
  601 and 604 while their host copies do not (`crates/victory-gpu/src/texture.rs`,
  how a change is detected: write watch or hash).
- **The world frames do not repeat.** Frames 2327-2334 are all different;
  at 1-2 fps the cutscene's clock runs on in real time, so each presented
  frame jumps far ahead of the one before (big camera moves between frames).
- Steady state as before: 0.3-1.4 fps, 4,600-5,200 draws, 480-800 dropped,
  texture preparation spiking to 3.3 s a frame. The process held 16 GB.

## Fixed after the second run

- **Shader cache keyed on the translator, not the executable.**
  `crates/victory-gpu/build.rs` hashes the translator's sources and
  manifest, the cache entry encoding (`shader_cache.rs`), `Cargo.lock` and
  `rust-toolchain.toml`; the key adds the translator's run-time settings,
  now also the host's widest wave, the view heap limit and the
  `VICTORY_WAVE_LOCAL`, `VICTORY_MESH_OUTPUT_STRICT` and
  `VICTORY_STRICT_JOINS` switches. Checked: a diagnostics run filled the
  cache, and the release build then found **883 of 883** shaders in it.
- **Movie frames.** A texture whose hash finds new contents while the guard
  reported no write is hashed at every check from then on
  (`Last::blind`, `crates/victory-gpu/src/texture.rs`), and the log names
  each one. Checked: in the third run exactly the movie's 9 planes (3 sets
  of Y 3840x2160 and Cb, Cr 1920x1080) were flagged, frames 590-612 are all
  different (before, they cycled through three), and the intro holds
  30 fps (about 6 ms of hashing a frame).

## What needs doing, in order

1. **Run again with the warm cache**, to separate first-run pipeline
   building from steady-state problems, and check whether the character's
   body draws now. Save the log as UTF-8 without line wrapping (the
   PowerShell `*>` redirect wraps lines at 120 columns).
2. **Missing draws**: the 9 untranslated shaders (6 distinct reasons), the 6
   refused host pipelines (find why D3D12 rejects them, with
   `VICTORY_D3D12_DEBUG=1` in a diagnostics build), and the unimplemented
   pipeline creation method at slot `0x218`.

   diagnostics build, and find whether frame generation or history reuse is
   behind them.
4. **Speed, cheap first**: try the README's switches; then the structural
   items (CPU/GPU overlap, per-page detiling, the slow 14-20-pipeline
   submissions).
5. **Light in shadow**: finish the ray-tracing path (the largest item).
