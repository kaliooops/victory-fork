## How to build and run

```powershell
cargo build --release -p victory                                  # release
cargo build --profile diag -p victory --features diagnostics      # diagnostics
cargo test --workspace --release                                  # 497 tests, all pass
.\play.ps1            # release, safe settings (no speed switches), ~2 fps in the world
.\play.ps1 -Diag      # diagnostics build
.\play.ps1 -Fast      # with the speed switches (~4 fps)
```

The log goes to `victory-data\last-run.log` (unwrapped). The world takes
2-5 min to reach; the user plays to the prison and reports.

**Pitfalls learnt the hard way:**
- `VICTORY_SKIP_PIPELINES`, `VICTORY_CAPTURE*`, `VICTORY_GPU_TIMING`,
  `VICTORY_D3D12_*` work **only in the diagnostics build** (`-Diag`).
  Two tests were wrongly read because of this; `play.ps1` now warns.
- Changing the shader translator changes the shader cache key: the next run
  re-translates (~2 min) and drops many draws until pipelines are made.
- The missing-walls bug is **random per run** (roughly half the runs). Never
  conclude from one or two runs.

## Diagnostics built this session (diagnostics build)

- `VICTORY_CAPTURE=<dir>` + `VICTORY_DUMP_TARGETS=1`; create a file named
  `capture-now` in `<dir>` while the game runs: the next 3 frames are
  captured: picture, every render target, `frame-N-ops.txt` (every
  command, with bindings and drops), and **`frame-N-args.txt`** (each

## Open problems, by priority

1. **Walls and floors of the prison sometimes not drawn** (also the hair,
   sometimes). Proven with captures: the draws are `MS_VS_TransformD` with
   `PS_DeferredTextured` (main world geometry); in bad runs they are issued
   with **zero mesh groups** (e.g. args at `0xd49401ec0`: 106 groups good,
   0 bad). The counts come from the title's GPU culling:
   `CS_BatchCullInitArgs` (`9146291b38ea9ce1`) -> `CS_BatchCullMeshlets`
   (`3b471c122be79b3e`, static) / `CS_BatchCullPreSkinnedMeshlets`
   (`9f017d9011377efa`) -> mesh draws. The cull pass gets the same dispatch
   size in good and bad runs (268 groups) but outputs zero for the walls.
   Its inputs: two small batch buffers (`Srv s0+0` 288 B, `s0+8` 456 B), a
   1024x512 R32F depth pyramid (`Srv s0+16`, checked: not the cause), the
   174 MB geometry heap read through a heap slot (`u6`, title
   `0x1c920000+0xae00000`), outputs `Uav s0+24` (2 MB meshlet list) and
   `s0+32` (32 KB args). Ruled out: speed switches, dropped draws, refused
   pipelines, DirectStorage failures, the depth pyramid, and (probably)
   DirectStorage page writes. **Next:** compare the cull pass's input
   buffers between a good and a bad capture (the small batch buffers and the
   heap's ranges the walls' batch reads), e.g. read them back like the args;
   also check the CPU-written batch data's refresh path, and whether
   `CS_DefragHeap_ComputeRelocations` (refused, WaveSize 64, 128-lane
   groups, dropped every frame) moves geometry the cull then misses.
   The fork README lists this bug as known upstream.
2. **Speed: ~2 fps (safe), target 30.** Profile (prison): ~427 ms/frame =
   ~134 ms CPU prep + ~210 ms GPU + ~77 ms copy-back, all serial. GPU time
   is spread over ~1,300 pipelines; hair (~30 ms), skinning (~15 ms) are the
   heaviest; ~5,000 indirect commands each get a clamp dispatch between two
   full waits. `VICTORY_INDIRECT_WINDOW=1` tested: no gain. Speed switches
   give ~4 fps but are risky. Real gains need: CPU/GPU overlap done safely,
   fewer copies (UMA emulation), cheaper indirect handling.
3. Remaining refused pipelines: `CS_DefragHeap_ComputeRelocations`,
   `CS_AlphTransmissionPrefilterMip` (multi-wave groups, wave-wide form does
   not support them); one mesh pipeline (`f5e50eb2108c425b` +
   `ce3f0432a08f1d35`) refused in game but made offline (needs the debug
   layer).
4. Untranslated (8): double-precision wave sum (`CS_TransmissionVolumetrics`
   x2), lane mask where not every lane runs (`CS_ShadowRenderTiledCascades...`),
   `v_permlanex16_b32` (water), descriptor read as data (`CS_MinTimestepReduce`,
   `PS_PuddleDetect` x3).
5. Ray-traced lighting does not run, so whatever the sun does not hit is
   black (faces in shade). Largest job; see `docs/fork-ray-tracing.md`.
6. Black flickering blocks were seen only in diagnostics runs with capture.
